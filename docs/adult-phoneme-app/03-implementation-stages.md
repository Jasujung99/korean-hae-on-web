# 개발 1부터 6단계 상세 지시

## 공통 작업 규칙

작업 시작 시 브랜치·git status·기존 변경·실행 환경·AGENTS.md를 확인하고 기록한다. 기존 작업을 보존한다. 현재 본사이트의 루트는 Astro 정적 앱이며 `main` 변경은 Hostinger용 배포를 실행한다. 작업은 전용 브랜치에서 수행하고 운영 작업은 자동 실행하지 않는다.

기준 커밋과 실제 시작 상태가 다르면 현재 상태를 먼저 읽는다. `old-site/`·`old-design-system/`은 백업이고, 루트 `index.html`도 현재 배포 화면이 아니다. 디자인은 `src/design-system/README.md`, `tokens.css`, `base.css`, 현재 로고를 따른다.

개발 단계마다 변경·실행 명령·검증·미완료 조건을 기록한다. 필요한 외부 권한이 없어도 샘플과 실제 연결을 명확히 분리해 독립적인 작업을 계속한다. 필수 권한·음원이 없는 기능은 완료로 보고하지 않는다.

## 개발 1단계 앱 경계와 해온 디자인

### 작업

- 별도 성인 패키지 `apps/learn/`의 골격을 만든다. 기존 Astro 본사이트의 경로·루트 package scripts·배포를 유지한다.
- 앱의 세부 프레임워크와 서버 런타임을 실제 환경에 맞게 선택하고 `apps/learn/README.md` 및 짧은 ADR에 설치·실행·테스트 명령을 고정한다. 기존 Boa의 React 기반 패턴을 재사용할 수 있으나 어린이 앱을 복제하지 않는다.
- 정적 프런트와 서버가 나뉘어도 브라우저 관점의 `/api/*`는 같은 origin으로 제공하는 구조를 기본으로 한다.
- 해온 토큰을 재사용하거나 출처·버전을 기록한 로컬 토큰 어댑터를 만든다. 학습 앱 전용 상태색은 olive/ink와 wash 계열로 해석하고 별도 브랜드를 만들지 않는다.
- 듣기 퀴즈, 비교 도움, 마무리, 사전 확장, 교사 목록/상세의 화면 껍데기를 만든다. 미리보기 역할 전환은 개발 환경에만 둔다.
- 도메인은 설정값으로 주입한다. `learn.haeonkorean.com`을 이미 운영 중인 주소로 가정하지 않는다.

### 완료 조건

본사이트와 성인 패키지가 각각 실행된다. 루트 `npm run build`의 시작 전 결과와 수정 후 결과를 구분해 남긴다. 320px 모바일과 PC에서 핵심 조작이 잘리지 않는다. 키·DB 연결 없이 개발 화면을 볼 수 있다.

## 개발 2단계 콘텐츠와 커리큘럼 자료 구조

### 작업

- 공통 Stage 0~5, 대립 묶음, 발음 출현, 의미·학습용 버전, 문항·음원 판, 릴리스를 구조화한다.
- Boa PR #2의 추출기와 `inventory_id/entry_id/lexeme_key`를 참고해 원본 연결을 유지한다. 원본 seed·엑셀을 덮어쓰지 않는다.
- 첫 12개 후보에 대한 검수 양식과 승인 상태를 만든다. 실제 의미·예문 검수를 하지 않았다면 fixture를 `draft`로 둔다.
- 공통 문항·취약 후보·간격 복습 구분과 출제 정책 버전을 구현한다. 초기에는 균형 출제를 기본값으로 둔다.
- 자음 식별·ABX·뜻 확인의 과제 타입을 나누고, 화면에 표시한 과제 명칭과 집계가 일치하게 한다.
- 콘텐츠 운영 UI 대신 검수 파일과 검증 명령을 제공한다.

### 완료 조건

참조가 끊긴 문항, 목표 소리가 모호한 다중 출현 문항, 미승인 콘텐츠의 공개 편입을 검증기가 막는다. 새 ㄷ·ㅌ·ㄸ 대립 묶음을 테스트 fixture로 추가해도 화면·스키마를 새로 만들 필요가 없다. 이 fixture는 운영 목록에 자동 편입되지 않는다.

## 개발 3단계 대표 TTS와 고정 음원 파이프라인

### 작업

- `GEMINI_API_KEY`를 환경 변수로 읽는 로컬 제작 CLI 또는 서버 전용 도구를 만든다. 브라우저에서 Gemini 키를 사용하지 않는다.
- 생성 명령은 명시적으로 실행할 때만 호출한다. 테스트·빌드에서 실제 생성이나 비용 발생 호출을 하지 않는다. 키가 없으면 비밀값을 출력하지 않고 해당 연결 검증만 미완료로 남긴다.
- Flash TTS 기본 목소리의 짧은 표본으로 대표 음성을 선정한다. 초기 후보는 Iapetus이며 실제 선택은 청취 검수 뒤 고정한다. 목소리 설계·복제는 만들지 않는다.
- 요청 방식 하나를 선택한다. 사용자 제공 generateContent 방식을 사용할 수 있으며 Interactions와 응답 스키마를 혼용하지 않는다.
- 의사단어·단어·예문별 파일, 원본 MIME·해시·입력문·모델·목소리·설정·검수 상태를 저장한다. 원본 WAV와 배포본을 구분한다.
- 재생 실패·무음·잘림·재생 중 응답을 정상 정오답과 구분한다.

### 완료 조건

키 없이 fixture로 파이프라인을 시험할 수 있다. 실제 생성 검증에는 별도 실행 결과와 청취 승인 기록이 있다. 학습 중에는 고정 음원을 재생한다. 승인되지 않은 음원으로 평가 문항을 공개하지 않는다. 음원이 없으면 ‘아직 준비 중’으로 표시하고 무음 응답을 실제 성적으로 저장하지 않는다.

## 개발 4단계 개인 초대와 기기 세션

### 작업

- [개인 초대 계약](02-invitation-and-device-session.md)대로 교사 등록·일회용 초대·명시적 claim·기기 세션·재발급·폐기를 구현한다.
- Supabase의 기존 계정과 별개로 성인 역할·교사 배정·링크/기기 세션을 정의한다. 기존 `user_roles` enum과 `has_role` 권한을 편의상 넓히지 않는다.
- 새 스키마는 마이그레이션 파일로 준비하고 로컬 DB에서 먼저 적용한다. 운영 프로젝트의 초기화·reset·직접 SQL 실행은 하지 않는다.
- 사용자 확인 없는 초대 소비, 미리보기 봇 소비, 동시 두 번 소비, 폐기 후 재사용, 다른 학습자로 큐 전송을 막는다.
- 같은 학습자에게 재발급해도 기존 이력이 유지되는 동작을 구현한다.

### 완료 조건

개인 링크 최초 연결 후 토큰 없는 공통 주소에서 이어진다. 링크 미리보기 GET으로 연결되지 않는다. 중복 claim의 결과가 일관되고 두 기기로 동시에 사용되지는 않는다. 재발급·기기 해제 후에도 고정 학습자 ID와 이력이 유지된다. 기존 어린이 인증 토큰과 무관한 교사가 성인 기록을 읽지 못한다.

## 개발 5단계 듣기 퀴즈와 학습 기록

### 작업

- 첫 방문·이어하기에서 바로 듣기 퀴즈를 연다. `듣기 → 선택 → 확인 → 비교 피드백 → 다음 문항 → 마무리`를 연결한다.
- ABX 도움은 별도 과제로 기록하고 풀던 문항으로 돌아오게 한다. 첫 제출 뒤 정답 표시·재시도·추가 재생을 각각 구분한다.
- 원시 이벤트·멱등 전송·진행 저장·outbox를 구현한다. 서버는 문항 판에서 정답을 판단하고 클라이언트가 보낸 정오답을 신뢰하지 않는다.
- 초기 공통 평가/출제와 훈련을 구분한다. 표본 부족에서는 유형 라벨이나 강한 개인화를 켜지 않는다.
- 사전·예문과 내 단어는 확장 경로다. 승인 콘텐츠가 있으면 별도 기능 플래그로 연결할 수 있다. 승인 전에는 실제 학습 기능처럼 표시하지 않는다.

### 완료 조건

새로고침·네트워크 재시도·중단 후 복귀에서 첫 제출과 진행이 중복되거나 사라지지 않는다. 기록은 기기와 초대가 아닌 학습자 ID에 묶인다. 음원 오류가 오답에 섞이지 않는다. 과제·릴리스·음원 판을 과거 응답에서 추적할 수 있다.

## 개발 6단계 교사 관찰과 통합 검증

### 작업

- 교사 인증 후 담당 학습자 목록과 상세를 제공한다. 목록에는 별칭·초대 상태·최근 학습·관찰 기록·재발급을 둔다.
- 개인 상세에는 과제·위치·모음 맥락, 제시→선택 혼동, 첫 제출/재시도, 재청취·시간·중단/재개를 둔다.
- 활동 시간·전체 경과·음원 재생·화면 이탈/무응답의 정의를 화면에서 확인할 수 있게 한다. 겹치는 시간을 모두 더하지 않는다.
- 작은 표본과 서로 다른 출제 비중을 표시한다. 긴 체류를 집중도·곤란으로 판정하지 않는다.
- PC는 목록+상세, 모바일은 목록→상세로 구성한다. 키보드·터치·로딩·오류·빈 상태를 점검한다.
- RLS·API·초대 동시성·이벤트 중복·판 교체·기존 서비스 회귀 시험을 완료한다.

### 완료 조건

교사가 등록→전달→학습→재방문→관찰→동일 학습자 재발급의 흐름을 로컬/검토 환경에서 끝낼 수 있다. 권한 있는 담당자만 조회한다. 실제 연동 항목과 fixture 항목을 보고서에서 구분한다. 운영 반영용 마이그레이션·배포·롤백 절차가 검토 가능하게 준비되어 있다.

## 6단계 이후로 남기는 작업

운영 도메인 확정·DNS·실제 Supabase 적용·운영 배포·`main` 병합은 최종 검토 뒤 사용자 확인을 받는다. Core 60 전체 승인, 다화자 HVPT, 실측 음향 그래프, 이메일/Google 학습자 로그인, 참여 코드, 콘텐츠 운영 UI도 별도 확장이다.

새 화자 전이는 훈련과 다른 목소리 ID의 승인 자료가 필요하다. 같은 목소리의 새 파일로 대체하고 완료했다고 보고하지 않는다.
